# Slice 1 Design: Accounts & Betting Economy

Status: implemented and verified.

## Scope

This slice delivers a self-contained product: users sign up, optionally claim a
team as DT, place virtual-coin bets on weekly matches generated by round-robin
scheduling, see bets settle, and track a leaderboard. Match results come from a
weighted-random stub behind the exact interface the later simulation engine will
implement. Team competition standings and bettor performance are deliberately
separate views.

## Architecture

```text
apps/
  api/       NestJS REST and Socket.IO
  worker/    BullMQ lifecycle scheduling and processing
  web/       React, Vite, and Tailwind SPA
packages/
  shared/    Isomorphic domain types and pure betting logic
  core/      Prisma, wallet, lifecycle, settlement, and result engine
infra/       Docker Compose, PostgreSQL init, and nginx
```

PostgreSQL is the system of record. Redis backs BullMQ and pub/sub so worker
live-data events reach API WebSocket clients. Shared TypeScript types keep the
three applications aligned.

## Data model

- `User`: email, password hash, coin balance, creation time.
- `Team`: name, optional crest URL, and strength rating from 1 through 100.
- `DTAssignment`: unique user/team claim, claim time, formation, and tactics.
- `Round`: week number, open/close timestamps, and open/closed/settled status.
- `Match`: round and teams, scheduled timestamp/day, status, and JSON result.
- `OddsSnapshot`: match, market, selection, decimal odds, and computation time.
- `Bet`: user/match/market/selection, stake, locked odds, status, and payout.
- `LedgerEntry`: user, top-up/stake/payout type, signed amount, resulting
  balance, and creation time.

The schema may add identifiers and relational metadata required to make jobs and
wallet operations idempotent, while preserving these domain fields.

League standings and betting performance are derived read models, not mutable
database counters. Resolved match results are authoritative for the league
table, while settled bets are authoritative for bettor statistics.

## Key flows

### Weekly lifecycle

1. Monday opens the next round, generates ten round-robin pairings, assigns five
   each to Saturday and Sunday, calculates initial odds, and grants each user a
   200-coin top-up with a ledger entry.
2. Friday at 23:59 closes the betting window. The API rejects new bets for that
   round from this point onward.
3. A due-match processor invokes the stub engine at the scheduled slot, grades
   pending bets, credits winners using their locked odds, and records payout
   ledger entries atomically.
4. The round becomes settled only after all ten matches are resolved.

The worker schedules the first two transitions and performs a five-minute due
resolution sweep plus a boot-time recovery sweep. Idempotency makes overlapping
or retried work safe.

### Placing a bet

The user selects one match, market, selection, and positive whole-coin stake.
The API verifies authentication, validates the selection against the current
snapshot, and checks both `status === OPEN` and `now < bettingClosesAt`. It then
atomically debits the wallet, creates the pending bet with `oddsTaken`, and
writes the stake ledger entry. Insufficient funds return HTTP 400 and a closed
window returns HTTP 409 without any writes.

### DT claim and lineup

An authenticated user may claim an unclaimed team, subject to one team per user.
The DT can save a basic formation and free-form tactics record for that team.
The stub deliberately ignores this data.

### League table

The schedule forms a 38-matchweek double round-robin season. The active season
is derived from the latest global week number, so weeks 1–38 belong to season 1,
39–76 to season 2, and so on. `GET /api/standings` calculates every club's
played, won, drawn, lost, goals for, goals against, goal difference, points, and
last-five form from resolved matches in that season.

A win is worth three points and a draw one. Ties are separated by goal
difference, goals scored, wins, normalized club name, and finally team ID. A
resolved Saturday match updates the table immediately without waiting for the
Sunday fixtures or round settlement. Calculating from results keeps concurrent
or repeated settlement naturally idempotent.

### Betting performance leaderboard

`GET /api/leaderboard` returns all managers but only gives a rank after one bet
has settled. Rank is determined by settled net profit, ROI, settled-bet count,
wins, account creation time, and user ID. Net profit is `totalPayout -
settledStake`; ROI and hit rate exclude pending bets. Records with fewer than
five settled bets are clearly provisional.

Wallet balance is shown only as context because signup grants, weekly top-ups,
and pending stakes are not measures of betting skill. Pending count/stake are
reported separately, claimed-team identity is included, and the public payload
uses a safe manager alias without exposing email addresses.

The API sends initial `standings:update` and `leaderboard:update` Socket.IO
snapshots and replacement snapshots after relevant writes. Worker-originated
events travel through Redis after round top-ups and after any match resolution,
even when every graded bet loses and no wallet payout is created.

## Testing

- Pure unit tests cover probability/odds monotonicity, all market grading and
  payout boundaries, round-robin correctness, season boundaries, complete
  standings/tie-break calculations, bettor statistics/ranking, privacy aliases,
  and a seeded statistical sanity check for the result engine.
- Integration tests use `football_test` and exercise signup, round opening and
  top-up, odds locking and stake debit, late-bet rejection, deterministic result
  injection, exact settlement and ledger state, repeated/concurrent settlement,
  round completion, DT conflicts, the zero/result league tables, pending versus
  settled bettor metrics, exact profit/ROI/hit-rate arithmetic, privacy, and
  idempotent ranking snapshots.
- Browser automation is deferred, but the complete signup/claim/bet/settle/live
  league-table and bettor-leaderboard path must remain manually demonstrable
  through dev controls.

## Explicitly out of scope

- Detailed match simulation.
- Live/in-play betting.
- Combo or parlay betting.
- OAuth, social login, or email verification.
- Real-money coin purchases.
- Promotion, relegation, and external competition qualification rules.
